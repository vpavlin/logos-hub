Logos tooling

Run Logos core modules headless — and drive them like a real API.

logos-hub is a thin, ergonomic wrapper over logoscore: bring a declarative set of modules up together, then call them through a typed CLI, bash completion, and an MCP bridge — all generated from each module’s own live API. No app-specific code.

bash
$ logos-hub up kym                              # daemon + kym_core (deps auto-resolve)
$ logos-hub call kym kym_core createBudget --name Groceries
$ logos-hub-mcp kym                          # same API, now as MCP tools for an agent

#What it is

Every Logos app has a headless core module (kym_core, qaku_core, scala, loam_core, delivery_module…). logoscore can load and call them, but raw. logos-hub adds the layer that makes them pleasant and repeatable to operate — and it’s 100% app-agnostic; apps are just tenants.

▨ Profiles

A declarative set of modules + env + module-dir, brought up together in an isolated config dir.

↻ One-command bring-up

up starts the daemon and loads the set; logoscore resolves each module’s dependency chain.

⚲ Reflective CLI

Methods, parameters and types come from the module’s own module-info — never hand-maintained.

◆ Agent-native

The same reflection generates an MCP tool per method, so any agent drives it with typed tool-calls.

#Quickstart

You need the logoscore binary and a modules dir (portable linux-amd64 bundles). Then:

bash
$ logos-hub profiles                    # what can I bring up?
$ logos-hub up kym                       # start daemon + load kym_core (+ loam_core, delivery)
$ logos-hub ls kym                       # loaded / available modules
$ logos-hub describe kym kym_core         # the module's typed API
$ logos-hub call kym kym_core snapshot    # call a method → pretty JSON
$ logos-hub watch kym kym_core           # stream its events
$ logos-hub logs kym                     # tail the daemon log
$ logos-hub down kym                     # stop

#Profiles

A profile is a JSON file under ./profiles/ or ~/.logos-hub/profiles/:

profiles/kym.json
{
  "name": "kym",
  "modulesDir": "/path/to/modules",
  "load": ["kym_core"],
  "env": { "KYM_HUB": "1", "KYM_CORE_DATA": "{data}" }
}
  • modulesDir — a logoscore modules dir (portable linux-amd64 bundles).
  • load — modules to load on up; dependencies auto-resolve.
  • env — environment for the daemon’s modules; {data} expands to the profile’s data dir.

#Typed CLI

call takes named --flags, coerced to JSON per each parameter’s Qt type read live from module-info. No hand-written JSON — and a bad flag is a clear error, not a silent no-op.

bash
$ logos-hub describe kym kym_core
  createBudget --name <QString>
  addAccount --name <QString> --type <QString> --balance <QString>

$ logos-hub call kym kym_core addAccount --name Checking --type asset --balance 100
$ logos-hub call kym kym_core createBudget --bogus x
logos-hub: kym_core.createBudget has no --bogus. Parameters: --name <QString>

$ logos-hub call kym kym_core createBudget --name X --dry-run   # show the JSON, don't invoke
$ logos-hub describe kym kym_core --json                        # full machine-readable schema

A raw JSON positional (call … createBudget '{"name":"X"}') still works. Because it reflects module-info at runtime, adding a method to a core surfaces it automatically — nothing in the CLI changes.

#Bash completion

Dynamic completion walks the same reflection: subcommand → profile → module → method → --param flags, live from the running daemon.

bash
$ source <(logos-hub completions)                                # this shell
$ logos-hub completions | sudo tee /etc/bash_completion.d/logos-hub  # persistent

#MCP bridge agents

logos-hub-mcp <profile> is an MCP server (JSON-RPC over stdio) that turns every invokable method into an MCP tool — named <module>__<method>, with a JSON-schema inputSchema derived from the Qt parameter types. Any MCP client — Claude, an agent runtime — then drives kym/qaku/scala/loam with first-class typed tool-calls, no CLI string-mangling.

bash
$ logos-hub up kym          # bring the daemon up first
$ logos-hub-mcp kym         # speaks MCP over stdio
# tools/list → kym_core__createBudget, qaku_core__addQuestion, … (generated live)

MCP client config: command logos-hub-mcp, args ["kym"]. The tool list is generated from the loaded modules’ schema; add a method to a core and it appears on the next tools/list — zero code change here.

#The shared multi-app hub

A profile can load several app cores into one daemon — and because logoscore loads each module as a singleton by name, they share one delivery_module — one Waku node. That’s the server-side mirror of the mobile Loam shared node: N per-app hubs collapse to one, saving relay, discovery and store overhead.

profiles/crib.json
{ "name": "crib", "load": ["kym_core", "qaku_core"], /* one node serves both */ }

Proven: kym_core + qaku_core in one daemon, exactly one Waku node started, qaku reusing kym’s already-loaded delivery_module. Getting it production-ready means minding a few things:

  • Include the full transitive dep set in the modules dir (e.g. loam_core needs ble_mesh) — a missing dep reads as “cannot resolve”, not a port error.
  • Version-align the shared modules — one delivery_module serves every tenant.
  • Pass the fleet entryNodes so the one node actually meshes; whichever core starts it first sets the config.
  • One node = one port — retire the per-app hubs rather than running them alongside.
  • A shared hub is a single point of failure — pair it with the peerless watchdog.

#Config

  • LOGOSCORE — path to the logoscore binary (default ~/logoscore-new/result/bin/logoscore).
  • LOGOS_HUB_STATE — where per-profile config/data/logs live (default ~/.logos-hub).

Each profile runs in ~/.logos-hub/run/<name>/{cfg,data,daemon.log} — fully isolated, so one hub never reads another’s registry.

Note — the typed CLI and MCP bridge are verified working against the kym_core + qaku_core set. The reflection is generic, but give a new profile a quick pass with its daemon up before leaning on it in an agent loop.
